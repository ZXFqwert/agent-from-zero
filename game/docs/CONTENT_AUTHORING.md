# 内容编写与验证

当前规范对应 v0.3 前两章。新增章节须同时登记剧情、解锁图、参考路线与 chapter-packs.json。配置描述世界，不能直接执行脚本，也不能由动画宣布胜利。

## 关卡与规则

`src/engine/types.ts` 定义 `ScenarioDefinition`；`src/content/chapterOne.ts` 是实际示例。每关声明 ID、版本、初始世界、可观察字段、操作前置条件与效果、实际完成条件、概念和资源限制。固定效果关使用 v2；协议关使用 `engineVersion: 3`。`world` 是现场事实，`observed` 只接收已经执行的观察、已接通的回执和验收；策略不能从世界事实偷读答案。

- `cost`、`failureCost`、`verifyCost` 都是公开游戏能量。失败成本由实际前置条件决定，不能将它当作预先泄露隐藏事实的信号。
- `missionBudget` 是整项委托资源，`blueprint.budget` 是一次派遣上限。重新派遣和换装不补充整项资源；重置同时恢复世界和资源。
- `toolCapacity` 限制同时装备的法器。反馈、验收回路可以保留，但当前未装备的工具不能执行。
- `hooks` 是一次性的确定事件，支持指定调用后或成功操作后触发、条件、效果和环境/不可信报告。真实变化会撤销相关旧验收；不可信报告不能成为伙伴已知事实。
- `goals` 必须同时符合实际世界与有效验收证据。`goalOrder` 只改变策略处理先后，不能删除完成条件。
- `transferRequirement` 指定成功的玩家手动操作或实际执行之间的法器换装。未用提示且有对应操作证据，才记录独立决策；它不证明真人已经理解。

旧三关的 v1 内容及 `legacy-v1.ts` 已冻结，用于旧存档和历史回放。不要改写旧规则或事件文字后还声称相同版本可重放。更改规则需新的关卡/内核版本以及明确的迁移策略。

## 剧情、进度与表现

`chapterOneStory.ts` 与 `chapterTwo.ts` 提供逐句对话、NPC、价值选择、三层复盘和根据实际世界条件显示的结局。选择的关系回应由 `narrative.ts` 和 `CityLedger.tsx` 展示；支线的服务地点必须来自搬运后的世界事实，不能用结算按钮追认已经执行的路线。`progression.ts` 用前置依赖图开放任务，支线不阻塞主线，旧首领访问权保留。

世界值使用普通布尔、数字或字符串；中文显示放在 `presentation.ts`，技术回放保留原值。新增美术需在 `Scene.tsx` 实际预载并依据世界状态切换；文字不烘焙进图片。PNG 原稿不发布，公开 WebP 放在 `public/art/`，来源和转换记入 `ART.md`。

## 参考解、错误与恢复

每个新关都写可执行的参考路线和至少一条错误后恢复路线。存在合理替代构筑时也要单独记录。`chapterOneWalkthroughs` 分阶段声明装备、实际调用、预期消耗、中途世界与失效证据，最终必须真实获胜。请通过实际错误制造资源/证据问题，不安排“无论怎样都会失败”的教学脚本。

```powershell
npm run validate:content
npm test
npm run build
```

内容校验检查普通数据、字段与引用、依赖图、故事关联、官方档案元数据、美术预载，以及 12 条新关参考/替代/恢复路线；通过固定 reducer 执行路线并核对状态与消耗。构建会先执行该校验。

外部内容包用 `npm run validate:content -- --json path/to/bundle.json`。必须是含关卡、依赖、故事、NPC、档案和路线的完整内容包；只解析 JSON，限制 8 MiB，拒绝函数、getter、特殊原型、危险键和循环，不执行外部代码。此入口仍使用已实现的关卡机制约束，不是任意第三方关卡插件。

档案需核查日期、文档版本或源码提交、官方来源和教学简化。验证器只能核对网址归属与数据完整性；发布新产品结论前仍需阅读官方正文。实际手机试玩、乐趣、迁移学习和整季时长不能由内容校验或自动通关代替。

## v3 工具协议

`protocol.parameters` 指定类型、必填、范围、枚举和界面选择；`defaults` 可以故意错误，但正确输入必须可以直接成功，不能安排必败剧情。`variants` 只声明参数条件、事实效果、整数库存变化和数量保护，不运行任意代码。数量更新原子执行，负库存拒绝；错误请求有公开通信成本，非法动作/错误配对则被整体拒绝而不扣资源。

每次调用分配新的 `callId`。`delivery` 可为立即、待归档或第一次成功后丢失；未送达的物理结果不进入伙伴上下文。玩家 `receive` 必须匹配真实回执编号；自动收录能完成世界任务，但不能冒充独立手动配对。`receiptCount` 按成功的不同操作计数，不按反复点同一操作计数，且使用提示不会获得独立迁移标记。

业务凭证另由 `requestKey` 指定。游戏执行器只保存已成功业务的指纹（操作 + 保留类型的参数）和原回执；同键同请求不重复执行，同键不同请求冲突。新调用仍消耗通信资源，旧回执也可能过期，必须另做现场验收。这是本游戏的执行协议，不能说成 LLM、Chat Completions 或 HTTP 自动提供了这个保证。自动构筑中的固定凭证按本关操作编号生成；一个操作在当前委托中代表一笔业务，多笔业务需另设计身份与策略。

`toolArguments` 在工坊存储确定参数，自动策略才能使用；这不是模型权重训练。继续保留冻结 v1/v2 的行为与历史事件。v3 的规则变更也须新版本和迁移，不可改完后假装旧轨迹仍然相同。

## 分章资源

`chapter-packs.json` 声明共享图片和各章图片。生产构建检查身份、资源存在与所有公开图片的归属，内容校验检查每个已制作章节都有分包、每关主场景位于正确分包。程序/界面共享，各章场景精灵分别下载；Phaser 只预加载当前章节的纹理。每包分别存储完整标记，逐项核验字节数与 SHA-256；部分下载失败不能擦除其他章或旧版本。更新继续由安全检查点显式激活，不在安装时抢占任务。


## v4 回路与第三章

已发布的 v1/v2/v3 保持冻结，新场景声明 engineVersion 4。blueprint.loopPolicy 的 maxCalls 为本次派遣请求上限（1–64），maxRetries 为短暂故障的额外重试（0–8），permanentFailure 选择 stop 或 repair。能量、调用次数与重试不是同一个计数；总能量不得通过重新派遣、换装、刷新补充。

操作 failureKind 默认为 permanent；temporary 可配 retryWindow（attempts、readyFact），用于明确写在现场规则中的冷却装置。窗口就绪只改变世界并产生未交付的环境事件；下一次观察或工具回执才改变伙伴的知识。永久故障需要停止介入或按已收到的前置条件寻找修复动作，不能靠偷偷改世界让它成功。

控制器记录 dispatchCalls、各操作尝试/失败次数、最后交付的失败与停止原因，均参加严格重放。配置和重派可以明确开始新轮；暂停/继续保留当前轮计数。成功验收优先于耗尽，未成功且能量归零时优先报告能量停止。自定义故障字段不得用于旧内核。

参考路线 stages 可声明 loopPolicy；它必须经过同一蓝图校验。新增章必须注册剧情、解锁依赖、所有目标事实、独立离线包和 Phaser 纹理，并提供 reference 与 recovery 路线。第三章已有 16 条，详见 CHAPTER_THREE_QA.md。不要把正确参数、临时故障和需要修复条件的故障混为一类；提示、剧情与可见规则必须一致。

历史证明从旧版信封迁移到 season-0.4.0；旧版不能夹带当时未发布的章节。引导重打可更新当前进度，但不能抹掉先前更强的独立迁移历史，也不能再次发放契约数量。
