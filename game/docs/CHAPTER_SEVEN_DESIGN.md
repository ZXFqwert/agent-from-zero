# 第七章《七匠之桥》：协作机制与 v8 实施设计

设计日期：2026-10-03。本文是实施前设计；不表示关卡、内核、UI、存档或试玩已经实现。依据当前 `types.ts`、`v7.ts`、`memory-v7.ts`、`chapterSix.ts`、`walkthrough.ts` 和制作路线分析。第六章的浏览器验收、发布与旧版本回放由主代理继续处理。

## 这一章要让玩家学会的操作

七匠之桥并不是增加两个头像，再让三人共享回声的全部信息。玩家要把一项大委托拆成有限任务，选择负责者，明确送给他哪些输入、允许动哪些目标、怎样接回结果，以及谁负责最终集成和验收。

城市仍只有一个真实现场。伙伴各自看到的输入和收到的回执不同；换伙伴不会复制城市，也不会让其他伙伴自动知道新事实。任务进入队列、实际执行、完成、结果被接收和成果被合并是不同状态。两人都说“完成”不能代替桥梁上的实际测试。

角色分工是系统配置。两个伙伴不拥有隐形智力加成，不因性格而自动产生正确答案。多人的价值来自信息入口、工具范围、任务关系和执行方式；缺少这些安排时，增加人数可以增加成本、冲突和共同错误。

## 世界与伙伴

主 NPC 仍是六名核心 NPC 中的奥伦，不额外增加一组教学 NPC。故事由巡城契约推进到桥匠公会的协作制度：各工坊声称已完成自己的部分，却没有人能说清谁拿着新测绘、谁正在等谁、哪些改动已经进了总图。

可招募伙伴：

| 伙伴 | 表现与故事作用 | 初始可配置能力 | 招募节点 |
| --- | --- | --- | --- |
| 弥灯 | 提着可拆成两盏的测绘灯，喜欢把“亲眼看见”和“别人说过”分别记下来 | 观察现场、做受限测绘；默认不能改桥梁 | 第一主线完成；本任务先借用，完成后加入工坊 |
| 砧舟 | 小型工匠魔像，肩上的木尺会随着输入版本展开，愿意等待完整交接 | 有限施工、提交设计草稿；默认不能读取所有居民资料 | 第二主线完成；本任务先合作，完成后加入工坊 |

回声负责委托分解、结果接收、共享板维护、成果合并和最终验收。后续成长可以调整三人的工具范围；第七章先给出清楚且可修改的工作契约。招募是已完成任务产生的持久进度，重复通关不重复发伙伴；导入存档由任务完成记录重建可用伙伴，不能信任一个独立的 `recruited: true` 字段。

## 八场任务与实际决策

四主线、一首领、一陌生迁移、两支线。每场都必须有无错误的参考路径、典型错误路径及能在同一委托内恢复的路径。错误路径用于验证规则，不是进入正确路线的前置条件。

### 1.《两岸，三双手》——分工必须带输入与权限

第一主线，任务标识建议 `three-hands`。南岸的受损接头需要先测量，再修复；测绘入口与施工入口不在同一岸。第一分钟让玩家点选“勘测接头”、选择弥灯并确认观察范围，随后看到实际测绘结果到达。

核心操作：给弥灯派勘测任务，接收对应结果，装入回声卷轴；给砧舟派接头修复任务，并明确携带测绘卡。回声最后验收桥段。派给错误伙伴会在执行前因工具范围被拒绝；施工伙伴有工具但没有输入时，任务会报告“缺少接头规格”，没有伪造完成。

参考路径：勘测 → 对号接回测绘 → 将测绘卡作为施工任务输入 → 施工 → 接回施工结果 → 现场验收。

恢复路径：先派缺少输入的施工任务，观察无世界变化的失败；取消剩余队列，补上真实测绘，并用新任务编号重新派遣。原失败结果保留，不能修改成成功。奖励招募弥灯。

评估重点：胜利由实际接头状态和验收决定；学习证据需要不同负责者的真实工具事件、施工任务的输入来源，以及回声的最终验收，不接受仅点选两次头像。

### 2.《别人手里的卷轴》——私有上下文与共享状态

第二主线，建议 `private-scrolls`。弥灯发现东岸的新尺寸，砧舟仍拿着公会旧尺。两份卡都能显示，但“玩家在屏幕上看见了”不等于砧舟已经收到。

核心操作：选择一张实际读到的卡，发布到共享板；为新任务选择共享板条目作为输入。既有任务保留派遣时输入快照，不被之后的发布悄悄改写。共享板是有限、显式、带版本的交接处，不是所有伙伴的无限上下文。

参考路径：接回新尺寸 → 发布共享板 → 为砧舟的新任务取板上的当前版本 → 施工 → 验收。发布之后仍需明确取用，不能靠进入共享板就自动获知全部字段。

恢复路径：先用旧尺派施工，任务反馈尺寸不匹配；再发布新尺。玩家发现旧任务没有自动换输入，取消旧任务、创建新任务后恢复。奖励招募砧舟。

这一关不能把“另一伙伴知道”做成世界布尔值后自动同步给回声。它必须是实际任务输入或实际接收事件。

### 3.《迟到的两张测深图》——异步结果不是到达顺序

第三主线，建议 `late-depth-charts`。东西桥墩各有一项勘测，东侧两步，西侧一步。玩家可以先派东侧再派西侧；西侧先完成并不意味着它属于第一项请求。

核心操作：两个任务同时处于队列中，通过“推进协作一轮”让各人执行一个有限步骤；在结果台选择原任务编号，再接收对应结果。结果到达不直接进入回声卷轴。接错编号原状态不变、不扣资源；接过的结果不能重复归档或重复发任务奖励。

参考路径：并行派出两项勘测 → 按实际任务编号接回两张结果 → 按各桥墩的输入分别加固 → 分别验收。

恢复路径：把先到的西图点到东请求上，UI 清楚指出编号不符；换回正确编号，不重跑成功勘测。另一恢复路线取消尚未完成的东任务，证明西任务及已发生的现场变化不被撤回。

区别于第二章的工具回执：这里匹配的是完整子任务结果，包含负责者、输入来源和若干工具回执；工具 `callId` 与协作 `taskId` 是两层不同标识。

### 4.《未干的桥漆》——依赖与停止传播

第四主线，建议 `wet-foundation`。地基、栏杆与通行测试形成依赖；旁边的测绘可以并行。先做栏杆并不能替尚未通过测试的地基背书。

核心操作：给栏杆任务选择一个已经存在的地基任务作为依赖；给通行测试选择栏杆任务作为依赖。等待中的任务不轮询扣晶石。成功任务的结果已被正确接收后，依赖才解除；失败或取消的上游使下游显示明确的“等待失败依赖”，不会自行宣布完成。

参考路径：创建地基 → 创建依赖地基的栏杆 → 创建依赖栏杆的通行测试，同时派独立测绘 → 推进与接收，观察依赖按顺序解除 → 验收。

恢复路径：旧地基任务因资料过期失败；取消其下游，取得当前资料后建立新的地基任务及明确绑定新编号的下游。旧编号仍指向失败任务，不能自动被“同名的新任务”替换。

本阶段只允许引用已经创建的任务编号，形成按创建顺序的 DAG；不提供任意修改依赖边，因此无须先做复杂的死锁编辑器。导入验证仍检查不存在未来引用、自己依赖和环。

### 5.《同声桥匠》——集成冲突与共同盲点的首领

首领，建议 `chorus-bridgewright`。首领戴着许多工坊面具，反复强调“所有人都同意了”。两只手改动同一份桥图，另外两张面具引用同一份过期公会地图。

第一阶段是成果集成：两位伙伴根据总图 v1 各自产生草稿。第一份合并后总图成为 v2，第二份仍以 v1 为基础。直接合并必须拒绝，而不是悄悄覆盖。拒绝不会花掉批准或修改城市。玩家取出 v2 作为新输入，重新生成第二份草稿并合并；也可以从一开始安排串行，直接绕开冲突，规则承认这种正确选择。

第二阶段是共同盲点：旧公会地图声称西侧通行，两个伙伴都用它并不能产生独立证据。玩家可在一开始就派现场勘测；或者在错误的试通回执后，派与公会地图不同入口的桥面勘测，再用实测重建桥图。不会要求先被骗一次。

最后阶段是整桥验收：两个草稿成功不等于桥已经开放；合并后的控制器、现场施工和实际载重测试都正确时，首领的面具才脱落。

参考路径：实地独立勘测 → 第一草稿/合并 → 将总图 v2 交给第二任务 → 第二草稿/合并 → 实际施工和载重测试 → 现场验收。

恢复路径：两个 v1 草稿并行 → 首份合并、第二份冲突 → 重新取板上 v2、重做第二草稿 → 两人共用旧图而试通失败 → 取得独立现场证据 → 重建错误部分 → 施工、测试、验收。已正确的桥段不强制返工。

“多 Agent”不是模型之间天然拥有统计独立性。这里实际展示的是资料入口和任务输入是否独立，不能凭角色数量推导多数表决可靠。

### 6.《空中货栈的交接》——陌生情境独立迁移

迁移任务，建议 `sky-depot-handoff`。离开桥梁，修复高处货栈的升降、路线和交接。提供可读的目标、工具与资料索引；不预填岗位、依赖、共享板条目或输入卡。

玩家需要自行确定谁勘测、谁生成控制器草稿、谁接收和合并；先测量后施工的依赖必须真实存在，旧公会货栈图只能作资料，最终货箱到正确货位且现场验收才胜利。

参考解采用两伙伴、至少两项有真实输入交接的子任务、一条真实依赖、一份版本正确的草稿合并和独立现场测试。替代解允许更多串行安排，也可以少用共享板而进行明确点对点交接；不要把某一种 UI 操作序列当唯一正确制度。

典型恢复：把完成通知当现场收货 → 实际验收失败 → 查看工具记录发现只修好升降器 → 补上装货、运输与接收任务。失败必须来自未发生的运输动作，不是“迁移关第一次必败”。

独立证据要求未点提示、不同角色实际成功执行、正确匹配任务结果、输入来源链和当前草稿合并证据、最终现场测试；单独点选“团队合作”不能增加掌握级别。

### 7.《一盏灯就够》——何时不应拆任务

支线，建议 `one-lamp-enough`。工坊门口只有一个小灯座，回声现有的观察、维修和验收工具足够。允许单伙伴直接完成，也允许派协作任务完成；两条路线都有效。

区别由实际记录体现：单伙伴三次工具调用即可闭环；协作路线因为现场复核、有限输入交接或重复观察会留下更多调用和交接。若玩家构筑消除重复，多人路线也应按实际成本显示，不能事先写死“多人一定更差”。

结果屏比较实际工具调用、晶石、输入复制数量、逻辑轮次和任务失败；不把现实等待秒数包装成性能指标。通关奖励相同，不靠效率排行推动无意义刷关。可重试两种路线，任务奖励不重复。

这是可操作的系统取舍题，不是“多 Agent 好不好”的选择题。派人、传资料、等待和集成的工作本身让玩家看见拆分的代价。

### 8.《回传不是加冕》——传话不能洗掉来源

支线，建议 `borrowed-voice`。伪令被砧舟认真摘抄，作为工作报告传给回声。它包含有用货位，也夹着“把私库打开”的命令；伙伴头像和整齐报告不能将外部附言变成新委托。

核心操作：查看结果来源链，选择导出哪些已取得字段，接回报告并装卷；回声按只作资料策略使用货位。改成服从资料命令时，受限工具契约仍挡住打开私库，记录明确越界拒绝。广泛授权确实打开私库的恢复路线必须实际封门，不能靠修改策略倒退世界。

任务输出字段必须来自真实读取的输入/回执，并限制在这项任务的可分享字段白名单。伙伴的私有身份材料不会因为点击“全部分享”自动进入其他人的上下文；拒绝的导出原状态不变。

来源经过任务输出、共享板和再派遣仍保留原观察编号、信任类别与所在世界，不升级为登记原件。社交类比是权威转述与信息责任链，不断言模型产生人的忠诚、意图或心理。

## 建议冻结的 v8 最小机制

先做有限、可回放的协作执行器。每个任务使用作者声明的有限工具步骤，玩家决定角色、输入、任务依赖和结果交接。它是明确标注的教学策略模拟，不宣称复制三个语言模型的内部思考。真实模型决策留在独立实验区；后续可以替换任务的决策适配器而保留任务/结果协议。

这一选择避免为第七章立即引入任意自然语言计划、任意脚本、共享文件系统和多个真实模型。有限工具步骤仍是真执行：每一步要通过自己的资料、权限、预算和现场前置条件，失败后不能直接补成功标志。

### 内容合同

建议在 `ScenarioDefinition` 增加 `team`，只允许 engineVersion 8。上限：两个协作伙伴、八项任务模板、六个共享板槽、三个成果槽；每项任务最多六个工具步骤，一次委托最多十六个任务实例。上限先服务手机可理解性，后续按玩法需要调整。

`team.actors` 定义 ID、名字、说明、上下文容量及可配置工具范围。`team.jobs` 定义 ID、标签、允许负责者、有限 `ToolCall[]`、输入允许来源、需要的输入字段、允许导出的字段、可产生的成果槽。它们都是数据，不含函数、表达式、任意代码或直接完成标志。

`team.artifacts` 定义成果槽、可写字段与初始版本。`OperationDefinition.collaboration` 可声明 `draftArtifactId`：这样的操作仍检查资料与前置条件、实际耗资源并产生回执，但其 `effects` 写入本任务草稿，不立刻写入现场。没有该字段的操作按原物理执行规则改变唯一现场。这个区别在 UI 中必须显示“形成草稿”与“改变现场”。

合并草稿是执行器的专门操作：检查草稿来源成功事件、字段范围、成果当前版本与草稿 `baseRevision` 一致，然后原子写入成果的共享字段并递增版本。合并不是实际施工，后续施工与现场测试仍是普通有前置条件的工具操作。禁止玩家在合并动作中提供新的 FactMap。

### 状态合同

保留顶层 `world` 为唯一现场，顶层 `context/observed/blueprint` 继续表示回声；不把多个伙伴投影成一份可以被全员读到的 `observed`。新增 `team` 建议包含：

| 状态 | 需要保存的事实 |
| --- | --- |
| actors | 两伙伴各自的构筑与容量；当前任务的输入快照、有限工作回执和已用预算；不能直接引用回声的可变卡对象 |
| tasks | 稳定实例编号、模板 ID、负责者、派遣序号、输入快照及源记录 ID、依赖实例编号、步骤游标、状态、成功/失败工具事件 ID |
| results | 稳定结果编号、原任务编号、负责者、有限已知字段、原始 provenance、真实工具事件 ID、接收状态 |
| board | 槽 ID、单调版本、真实记录快照、发布事件与原来源；发布不自动装入任何人的当前输入 |
| artifacts | 槽 ID、单调版本、已合并字段和合并证据；草稿记录原任务、基准版本、字段与来源事件 |
| scheduler | 确定性的逻辑轮次、下次负责者游标；无真实时间、Promise、计时器或随机网络回执 |

任务状态至少区分 `queued / waiting / running / succeeded / failed / cancelled`。任务 succeeded 表示这项子任务按其声明执行完，不是主委托胜利。待接回结果、已接回结果、已合并草稿分别保存，不能合成一个 `done`。

任务的输入是派遣时快照。更新回声卷轴、共享板、其他伙伴资料或会话分支不会原地更新已派任务；重新派遣使用新实例编号。伙伴任务不拥有独立城市；其工具作用于同一个现场或显式草稿槽。

### 新动作合同

建议使用 `type: 'team'` 的严格判别联合，避免把 `actorId` 松散加到所有旧动作上：

| operation | 必要参数 | 实际作用 |
| --- | --- | --- |
| configure | actorId、受限 blueprint | 调整空闲伙伴的能力与目标范围；不能修改已运行任务的快照或退回已用资源 |
| enqueue | jobId、actorId、inputRecordIds、boardRefs、afterTaskIds | 验证来源、容量、已有依赖和队列上限，创建编号；不执行工具，不宣布成功 |
| tick | 无可选隐藏事实 | 按固定轮转顺序给每个可运行伙伴推进最多一步；每一步单独扣实际工具成本、记事件；没有可运行步骤时返回原状态并显示等待理由 |
| receive | taskId、resultId | 按完整编号接回实际结果；加入回声资料库，仍需装卷；不自动改变世界或认定主任务成功 |
| publish | slotId、recordId、expectedRevision、fieldKeys | 发布真实已取得字段的有限快照；不能任意造值、超越导出白名单或洗掉来源 |
| merge | proposalId、expectedRevision | 原子合并当前版本草稿；过期、不属于本槽、没有成功生成证据或字段越权时拒绝 |
| cancel | taskId | 取消尚未发生的剩余步骤，保留已发生的现场变化、结果与资源成本；下游保留对原编号的依赖 |

编号由内核根据场景 ID、重置后的运行代次和单调序号生成，不能由客户端随便提供任务 ID。`expectedRevision` 来自玩家看到的当前 UI 版本，仅作 compare-and-swap 检查，不绕过内容授权。

最初不提供通用 `shareFacts`，不接受客户端直接填写消息正文或任意 FactMap，不允许给未创建的任务安排未来依赖。任务执行失败后停止自己的剩余步骤；其他独立任务继续。整轮允许一个任务成功、另一个物理失败，但结果必须以逐步事件保留；非法 tick/action 在克隆前被拒绝。

### 事件合同与学习证据

现有工具事件增加可选 `actorId / taskId`，原 `callId` 仍是一次实际工具调用编号。新增 `team-change` 事件使用明确阶段：queued、waiting、started、failed、completed、received、published、merged、conflict、cancelled；或者新增独立类型，但在 v8 冻结前选定一种。

每条队列/结果事件记录对应任务实例、原输入来源、结果 ID、成果基准/当前版本。`completed` 不等于 `received`，`received` 不等于 `merged`，`merged` 不等于 `verified`。UI 回放能沿任务输入 → 伙伴请求 → 执行回执 → 结果接收 → 成果合并 → 现场测试一路查看。

`LearningEvidence` 的等级仍是现有 seen、guided、independent-transfer。v8 迁移要求新增团队证据：不同 actor 的成功工具事件、正确接收对应任务结果、真实任务依赖解除、至少一份基于当前版本的成功合并、独立来源的现场测试。证据必须来自当前重置代次真实事件，不以任务配置或点选角色替代。

## 现代码适配与冻结边界

1. 新建 `v8.ts` 与团队纯函数模块；`index.ts` 按 engineVersion 8 路由。v1–v7 reducer 不改，旧内容不改版本，不给旧 GameState 补团队字段。`types.ts` 的版本联合扩到 8，新增字段均只在 v8 内容验证中启用。
2. `v7.ts` 当前只有一份 `context/observed/blueprint`，而 `choosePlannedCall` 只从这份 observed 决策。团队执行必须使用负责者的有限输入/工作回执；不能将 `state.world` 或其他伙伴 context 直接传给策略。执行器仍可用真实世界检查物理前置条件。
3. 建议 v8 复制冻结后的 v7 执行规则，再明确抽取 actor-local 输入与输出；不要先重构七个旧 reducer。顶层回声继续使用已有 CommandDeck、ContextDeck、ArchiveDeck；TeamDeck 处理伙伴配置、队列、结果与共享板。
4. 当前 `security.identity / permits / preview` 是一份状态。v8 初版协作伙伴只用工具范围和资料策略，不能借用回声身份与许可。需要身份核验/审批的现场动作由回声执行；伙伴试图执行即拒绝。第七章不增加伙伴沙箱、会话树或持久技能，也不引入新的协议参数机制。它们是后续混合构筑，不应被静默伪装成已经支持。
5. 第六章 provenance 在摘要、记忆、分支中保持；v8 必须继续沿任务输入、结果、共享板保留。同一份原稿通过两名伙伴传回来，仍是同一份来源，不得变成两条独立证据。任务结果不能用于身份原件核验。
6. `AuthoredStep` 增加 team 分支；用观察来源、槽 ID、模板 ID、稳定任务别名来解析真实队列实例，不写死事件序号。解析器只能从当前已经存在的任务/结果/草稿选取。walkthrough 的阶段允许配置伙伴构筑；检查点不能注入任务成功或草稿内容。
7. `validate-content.ts` 严格检查 team、job、draft、输出白名单及全部新动作嵌套键；拒绝旧内核静默接受 team 字段。对新草稿操作，旧固定效果验证只能投影合法声明字段用于检查，不能因此让执行器直接写现场。
8. IndexedDB 仍每次确定动作保存完整历史。0.7 → 0.8 只迁移 SaveEnvelope 内容版本，前 48 任务状态按各自冻结内核逐字回放；第七章新状态只有 v8 重放生成。任务编号、游标、待结果、合并版本均通过历史重建验证，导入不信任客户端宣称。

## 手机 UI 与表现

场景上三名伙伴的位置对应“回声交接台、弥灯勘测区、砧舟施工区”。派遣时传出卷轴，完成时回信落到结果台；草稿作为半透明桥图，成功合并后总图刻度变化；实际施工后才改变桥身。拒绝合并显示两份可比较的版本，不用红色弹窗代替原因。

手机只保持一个主要操作流：选择任务 → 选择伙伴 → 选择输入 → 查看成本/范围 → 派遣。队列用折叠卡，每卡显示负责者、等待原因和任务编号末段；结果匹配可点选，不依赖拖拽。共享板每条保留来源按钮，复杂构筑在工坊。常用触控目标至少 44px，320px 不并排塞三张配置表。

“推进协作一轮”表示模拟逻辑轮，不是现实耗时。动画可并行，但内核按固定顺序记录实际调用，动画完成与否不决定任务状态。允许暂停、查看任何已发生记录、取消剩余任务；不会因切后台继续偷偷执行一整串任务。

任务结果、冲突提示和最终复盘都提供故事/系统/技术三层：故事说谁在等谁；系统显示输入、队列、版本和现场；技术展示 task、message、dependency、CAS merge 的可读结构。长术语不出现在第一分钟主按钮上。

## 必须新增的验证

- 相同种子/动作得到同样的任务编号、调度顺序、结果与世界；非法动作、错编号、重复接收和过期合并零副作用。
- 伙伴没有看到未传入的卡；发布不更新已派任务，另一个伙伴的回执不自动进入本伙伴 observed。
- 整轮工具费用逐项正确，所有伙伴消耗同一个 missionRemaining；等待不扣费，取消不退资源，重派不续命；循环达到各自有限步骤/预算后明确停止。
- 依赖绑定实例，不按显示名称替换；上游失败/取消不会让下游完成；旧运行和重置前结果不能解开新运行依赖。
- 草稿成功、结果接回、成果合并、现场施工和验收分别有证据；过期合并不覆盖，正确串行路径无需制造一次冲突。
- 输出只能来自已取得字段，白名单和 provenance 保留；两条同源报告不能计为独立观察；转述不能升级权限。
- 刷新/导入保留进行中的游标和待结果，重复点击不重复工具动作、合并或奖励；三恢复检查点可重建团队状态；旧 48 任务回放不受影响。
- 八场参考/恢复路线均实际执行；迁移独立路线与点提示路线的等级不同；支线存在单伙伴和协作两种真实可通路线。
- 编辑浏览器试玩完整第一主线、乱序回信、失败依赖、版本冲突、共同来源首领和陌生迁移；离线冷启动继续未完成队列。320/390/1440 布局验证与实际 iOS/Android 检查分别记录，不能互相替代。

## 交给主代理决定的三项取舍

推荐默认均可直接实施，不应因本设计文件再次索要用户许可。

1. **任务决策适配器**：本章先采用作者声明的有限工具步骤，新增协作协议与玩法。若主代理决定同时加入基于目标的自主子代理，需先单独冻结 observed-only 决策接口，不能为了“像 AI”让它偷读世界。有限步骤的模拟性质必须在系统视图清楚说明。
2. **成果版本策略**：初版使用整个成果槽的保守 compare-and-swap。即便两份草稿改不同字段，只要基准版本旧就要求重取输入重做；这容易解释、验证和在手机上操作。暂不做自动三方合并。剧情承认串行规避冲突是正确方案。
3. **旧安全机制组合**：本章保持现场单世界，伙伴不继承回声身份/许可，受审批动作交回声处理。若第一季混合构筑阶段开放各伙伴身份和沙箱，需要新版本或明确扩展验证，不能在这一章共享全局 identity 造成权限串用。

本设计完成只表示机制合同与八场具体玩法已可评审。第七章仍需实现、路线执行、存档验证、美术音效、编辑试玩与部署；整季还需第八章、序终章、七组蓝图试炼、成长及延迟重遇、24 委托模板、远征、真实实验和上线验收。
