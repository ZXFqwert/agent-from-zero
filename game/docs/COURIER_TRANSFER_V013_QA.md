## 制作方桌面 Chrome 的实际操作

主实施者通过真实网页控件执行以下路线，未把内部参考实现或直接写入一份获胜状态当作浏览器通关。

1. 医院委托先使用提示，按调用编号查重后重复发送，医院实际收到两箱，现场验收失败。
2. 从起航检查点开始新虚拟尝试，改用业务键查重与持久账本；医院交付一箱。刷新后从存储冷读取，已提交交接与一箱现场仍在，未重新发送请求。
3. 在同一尝试中重启宿主并恢复账本，使用新调用编号和同业务键重试，医院仍为一箱；改成两箱的请求被业务账本拒绝，最后现场验收通过。由于此前已经看过此作者任务提示，本场只记录熟练操作，没有补成陌生独立迁移。
4. 切换到尚未看提示的夜市作者委托，按原件发送市集两箱；回执丢失后重启、恢复，使用新调用编号及原业务键重试，市集仍为两箱。随后同键改为一箱被拒绝，独立现场验收通过，形成新增迁移证明。

## 提示曝光、存档与回滚边界

签收站使用独立 IndexedDB `echo-courier-workshop`、`progress` 存储及 `courier-v1` 键。外层信封为 `echo-courier-progress`、版本 1，包含当前尝试、已取得的合法交付证明、作者提示曝光与提交修订号。每条完整尝试先按固定 `courier-v1` 作者规则回放，再比较保存的状态和事件；单尝试上限 128 KiB、64 个动作，备份上限 512,000 字节。归档最多三份，优先保留每份作者任务最早的合法证明。

提示曝光按作者任务跨尝试保留。提示先提交保存成功，再显示内容；看过提示的作者任务以后重新无提示通关仍只计练习。另一份未曝光作者任务可以提供迁移证明。已无提示取得合法证明后，在之后尝试看提示不会倒扣原证明。

独立对抗执行还验证了：导入较早的无曝光备份不会清除设备已有提示；设备已曝光作者任务的新增导入证明被过滤；原有合法证明继续保留；医院曝光不阻止未曝光夜市提供证明。备份导入先严格验证、预览确认，再合并设备现有曝光与证明。版本不兼容或回放失败时保留原数据，不用空记录覆盖。完整可编辑本机文件没有防作弊认证能力，界面明确它记录模拟操作，不认证人的理解或是否看过外部答案。

保存接口采用同一读写事务和修订号比较，旧页面持有过期修订号时拒绝覆盖。主页面只读或不持有原存档锁时，不执行签收动作。浏览器并发保存的实际验收需另行记录，不能用源码审查代替。

起航检查点会创建一个**新的虚拟尝试**：保留发货前装配与信息，重新演练后续操作；未完成尝试的后续动作会重置，提示曝光和既有合法证明保留。它不是对真实外部世界的撤销。与此不同，委托内的宿主重启保持同一现场，已经交接的药箱不会倒退。

旧主线模拟器、作者内容、长期挑战、`postSeason.ts` 与 `storage.ts` 未改；内容和主线存档继续使用原有版本与严格回放规则。新玩法、信封和补充课程证明位于独立模块，不进入旧主线信封。回到不支持签收站的版本时，旧主线仍按其兼容合同读取；旧版本没有新玩法入口，也不能读取签收站记录。新数据库保留，重新升级到支持其版本的客户端后才能继续。相同主线模拟摘要不能被解释为旧客户端能运行新模块。
